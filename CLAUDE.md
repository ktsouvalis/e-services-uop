# CLAUDE.md

Guidance for working in this repo.

## What this is

A Laravel 12 (PHP 8.2) internal admin/tools app ("e-services") for a university's Digital Governance Unit. Breeze-based scaffolding, MySQL, database-backed queue/cache/session, Vite + Tailwind frontend, Blade views (no SPA framework). Multiple unrelated internal tools live side by side in one app, each gated by a DB-driven, toggleable menu system.

## Stack

- Laravel 12, PHP 8.2, Breeze scaffolding (`laravel/breeze` dev dep, `routes/auth.php`). Upgraded from Laravel 11 on 2026-08-04 — Laravel 11 exited security support in March 2026, so CVE fixes stop appearing on that branch; stay current going forward rather than pinning to a major version. Pest is intentionally held on the `^3.2` line (not v4) since Pest v4 requires PHP ^8.3 and this app's containers run PHP 8.2.
- DB: MySQL (`DB_CONNECTION=mysql`). Queue/cache/session all use the `database` driver.
- `romanzipp/laravel-queue-monitor` — job run tracking + a built-in UI at `/jobs` (see `config/queue-monitor.php`; `ui.enabled` true, prefix `jobs`). The UI lets a user retry/delete/purge job records, so its route group's `middleware` array carries `App\Http\Middleware\AdminOnly` (added 2026-08-07) on top of the package's own `['web','auth']` default — it was previously reachable by any authenticated user, not just admins. **The `/jobs` table view is already overridden at `resources/views/vendor/queue-monitor/partials/table.blade.php`** (published from the package at some point pre-dating this file's history, and has since drifted from the vendor copy — e.g. the retry/delete Actions column is commented out there). Fixed 2026-08-07: the Custom Data column rendered `json_encode($job->getData(), JSON_PRETTY_PRINT)` without `JSON_UNESCAPED_UNICODE`, so any non-ASCII custom data (Greek department names, filenames) showed as `\uXXXX` escapes instead of text — added the flag. Since it's a Blade view, `php artisan view:clear` is needed after editing it if compiled views were ever cached.
- `phpoffice/phpspreadsheet` — used repeatedly for xlsx read/write (see `LogReaderController`, `ItemController`). Already a first-class way to handle spreadsheet import/export in this app, not a bolt-on.
- `directorytree/ldaprecord-laravel`, `laravel/reverb` (websockets, used for the chat feature — `App\Events\MessageSent`), `clue/redis-react`, `openai-php/client` (used by the Chatbot/AImodel features).
- Frontend: Blade + Alpine (via Breeze), Tailwind, Vite. No Livewire/Inertia present.

**Dev container gotcha**: `queue-worker` and `scheduler` both depend on the `database` service and will crash-loop with `SQLSTATE[HY000] [2002] ... getaddrinfo for database failed` if it isn't running — that specific error is DNS resolution failing for a *stopped* container, not a real networking problem or a code bug; check `docker ps -a --filter name=dgu-dev-db` for its actual status before debugging further, then `docker compose up -d database` (both crash-looping services self-recover via their `restart` policy once it's back). `database`'s host port (`DB_PORT_HOST` in `developing/.env`, default 3307) isn't namespaced against other projects on the same machine — if `docker compose up -d database` fails with "port is already allocated", something unrelated already owns it; change `DB_PORT_HOST` rather than touching the other container, since the app itself talks to `database:3306` over the internal Docker network regardless of this value.

## Feature-module pattern (important — follow this for new features)

Every feature area (Mailers, Sheetmailers, Items, Chatbots, Notifications, Menus, Log-reader...) follows the same shape:

1. **Migration** for its own table(s).
2. **Model** (`app/Models/X.php`) — typically `protected $guarded = ['id']`.
3. **Policy** (`app/Policies/XPolicy.php`) gating `viewAny`/`create`/`update`/`delete` — for most features the policy checks `Menu::where('route_is', $this->menu)->first()->enabled` (a hardcoded `route_is` string set as a property on the policy) **and** `auth()->check()`, i.e. authorization is menu-driven, not role-driven, except where `auth()->user()->admin` is checked directly (e.g. the `/get_logs` route in `routes/web.php`). **The menu-enabled check must be copy-pasted into every single method, not just `viewAny`/`create`** — `SheetmailersPolicy` and `ItemPolicy` both had `update`/`delete` missing it (found and fixed 2026-08-07), which meant disabling a feature's menu didn't actually block edits/deletes via a direct URL to an already-known ID, only the listing/creation. When adding a new policy method, check it against every other method in the same class, not just against `viewAny`.
4. **Every controller action needs its own `Gate::authorize(...)` call — there is no middleware-level enforcement to fall back on.** Several actions across this codebase were found with none at all: `AImodelController` and `MenuController` had zero `Gate::authorize` calls anywhere despite having real policies, and their routes also had no `auth` middleware, so they were reachable by unauthenticated guests entirely on request; `ChatbotController::destroy()` had no check, so any authenticated user could delete any other user's chatbot; `NotificationController::deleteAll(User $user)` trusted the `{user}` route parameter instead of checking `auth()->user()`, and its whole route group had no `auth` middleware, so any guest could delete any user's notifications by changing the id in the URL (all found and fixed 2026-08-07 while adding test coverage — see Testing section below). When writing a new controller action, treat "does this route have `auth` middleware *and* a `Gate::authorize` call for this exact action" as a checklist item, not something to infer from the route group looking protected.
5. **Gate registration**: only *some* policies are wired in `app/Providers/AppServiceProvider.php` (`Gate::policy(...)`) — others rely on Laravel's auto-discovery convention (`XPolicy` next to `X` model). Check both before assuming a policy isn't registered.
6. **Controller** — resourceful (`Route::resource`) plus extra `Route::group(['prefix' => 'x', 'middleware' => 'auth'], ...)` routes for non-CRUD actions (upload, download, send, toggle, etc). Controllers call `Gate::authorize(...)` per action rather than relying on middleware alone.
7. **Routes** all declared in `routes/web.php` (no route files per feature, no API routes — this is a server-rendered app only).
8. **Views** under `resources/views/{feature}/`.
9. **Logging**: features log to their own named channel, e.g. `Log::channel('menus')->info(...)`, `Log::channel('log-reader')->error(...)` — check `config/logging.php` for configured channels before adding a new one.
10. **File storage**: uploads go to `storage/app/private/{feature}/` (Laravel 11's default private disk root), accessed via `storage_path("app/private/{feature}/...")`, not the `Storage` facade's public disk. Files are often processed then immediately downloaded via `response()->download(...)->deleteFileAfterSend()`.

## Menu system (drives both navigation and access)

- `menus` table: `title`, `route` (route name to link to), `route_is` (route-name pattern used for both nav "active" highlighting **and** as the policy's authorization key), `enabled` (bool toggle).
- Rendered in `resources/views/layouts/navigation.blade.php` via `@foreach(App\Models\Menu::all() as $menu)` — skips disabled menus. **Menus are pure DB rows, not config/seeders** — adding a nav item for a new feature means inserting a `menus` row (via the `/menus` UI itself, which is behind `MenuPolicy`), not editing a blade file.
- A menu being disabled doesn't just hide the nav link — policies actively check `enabled` and deny access even via direct URL. Some features additionally gate an entire route group behind a small dedicated middleware that re-checks the same thing (see `App\Http\Middleware\LogReaderEnabled`, applied to the `log-reader` route group) — use that pattern when a route group (not a resourceful controller with Gate calls) needs the same "disabled in menu ⇒ 403" behavior.
- `MenuController::toggleEnabled` (`POST /menus/toggle-enabled/{menu}`) is the AJAX endpoint the UI uses to flip `enabled` without a full page reload.

## Auth / users

- `App\Models\User` has a plain `admin` boolean column (`2024_10_17_083949_add_admin_to_users_table.php`), checked directly with `auth()->user()->admin` in a few places (the `/get_logs` zip-download route) rather than through a policy/gate. Not every admin-only action goes through the Menu/Policy system — some just inline-check this flag.
- No roles/permissions package (no spatie/permission etc.) — authorization is entirely: session auth + the `admin` boolean + the Menu-driven policies described above.
- **Two completely different login paths, gated by `app()->environment()`, not one Breeze flow reused everywhere:**
  - **Local/dev**: `AuthenticatedSessionController` (`routes/auth.php`, `/login`) binds against LDAP directly via `directorytree/ldaprecord-laravel`. It looks up a **local** `App\Models\User` row by username *before* even touching LDAP and fails fast with "Invalid credentials" if none exists — unlike production, it does **not** auto-provision a local user from a successful LDAP bind. If local login fails despite correct credentials and a reachable LDAP server, check whether the dev DB was ever seeded (`php artisan db:seed`) — a fresh `migrate:fresh` without `--seed` leaves `users` (and `menus`, `categories`, etc.) empty, and this is the actual failure mode, not an LDAP problem. `database/seeders/UserSeeder.php` has the known-good dev usernames.
  - **Production**: nginx (`production/deploy/nginx/site.conf`) gates every request through an `auth_request` to an Authentik outpost sidecar (forward-auth), then forwards `X-Authentik-Username`/`-Groups`/`-Email`/`-Name` headers to PHP-FPM. `App\Http\Middleware\AuthentikSsoAuth` (global `web` middleware, registered in `bootstrap/app.php`, no-ops outside `production`) trusts those headers and does `User::updateOrCreate` + `Auth::login()` on every request where the current session doesn't already match — this *is* the auto-provisioning production's flow has and dev's doesn't.
  - **The outpost session and the app's Laravel session are not the same thing, and logging one out doesn't touch the other.** The outpost issues its own forward-auth session cookie on the app's domain, separate from Authentik core's own session cookie on Authentik's domain — ending an Authentik core session does not invalidate an already-issued outpost cookie. Because of this, a plain Laravel `Auth::guard('web')->logout()` in production is a no-op from the user's perspective: `AuthentikSsoAuth` just re-authenticates from the (still-valid) outpost headers on the very next request. The nav's Log Out link (`resources/views/layouts/navigation.blade.php`) branches on environment: in production it hits the outpost's own `/outpost.goauthentik.io/sign_out` (proxied by nginx, same location block as the auth_request check) to actually end the forward-auth session; elsewhere it uses the normal Laravel `logout` route.
- **`production/source/` is a separate, un-synced copy of this codebase, not a symlink or submodule.** Changes made here under `developing/source/` (this file's own directory) do not automatically propagate — confirmed stale during the 2026-08-04 logout fix, where `production/source/resources/views/layouts/navigation.blade.php` still had the old, always-visible logout button after `developing/source`'s copy had already been fixed. Whatever the deploy/promotion step is, don't assume a `developing/`-only change is live in production.

## Routes of note (`routes/web.php`)

- `/health` — plain JSON `{"status":"OK"}`, unauthenticated (liveness probe).
- `/get_logs?date=YYYY-MM-DD` — admin-only, zips and downloads `storage/logs/*<date>.log` files.
- `/log-reader` — regex-based log line extractor over an uploaded file, outputs an xlsx of unique matches; gated by `LogReaderEnabled` middleware (menu-driven) rather than a policy.
- Chat feature (`/chat/send-message`) broadcasts via Reverb (`App\Events\MessageSent`) — this app has real-time infra already wired (Reverb + Echo), reusable for any future "live updating" UI instead of polling.

## Testing

Pest, `RefreshDatabase` applied to all of `tests/Feature` via `tests/Pest.php`. Real feature test coverage (Mailers, Sheetmailers, Items, Chatbots, Notifications, log-reader, and admin — Users, AImodels, Menus, `/jobs`, `/get_logs`, `/health`) was added 2026-08-07; before that the only tests were unmodified Breeze scaffolding.

- **Never run the suite with plain `php artisan test` in this repo — use `make test` (in `developing/Makefile`, one level up from here).** `phpunit.xml`'s `<env>` overrides (including `DB_CONNECTION=sqlite`/`DB_DATABASE=:memory:`) look like they'd isolate tests from the real dev DB, but they silently don't: the `application` container gets its entire `.env` injected as real process env vars via docker-compose's `env_file`, and PHP's CLI SAPI copies those into `$_SERVER` before any of PHPUnit's own bootstrap code runs. PHPUnit's env handling (even with `force="true"`) only ever touches `$_ENV`/`putenv()`, never `$_SERVER`, and Laravel's `env()` repository reads `$_SERVER` first — so `DB_CONNECTION=mysql` from the container wins regardless of what `phpunit.xml` says. Confirmed this was live and unnoticed: running the suite the "normal" way would have run `RefreshDatabase` migrations against the real dev MySQL DB and could have queued real emails through the live queue worker. `make test` passes the correct values via `docker compose exec -e ...`, which does override `$_SERVER` for that one exec and is the only thing that actually works.
- **Every menu-gated policy fatals on a missing `Menu` row, it doesn't just deny access** — `Menu::where('route_is', ...)->first()->enabled` calls `->enabled` on `null` if no row exists. Use the `enableMenu('route_is')` / `disableMenu('route_is')` helpers in `tests/Pest.php` before hitting any menu-gated route; don't hand-roll `Menu::factory()->create()` for this unless you also set `route_is` yourself.
- **`Menu::factory()`'s `route` attribute must be a real, permanently-registered route name, not a fabricated one** — `navigation.blade.php` calls `route($menu->route)` for *every* `Menu` row on *every* authenticated page (it renders the whole nav), so a fake value like `{slug}.index` throws a `RouteNotFoundException` the moment any test with a stray `Menu` row in the DB renders a normal page. The factory defaults `route` to `'dashboard'`, which always exists.
- **`UserFactory` does not set a `password`** — this app's `users` table has no `password` column at all (LDAP/Authentik auth only, see Auth section above); don't reintroduce Breeze's default `password` field if regenerating the factory.
- `tests/Feature/Auth/*`, `tests/Feature/ExampleTest.php`, and `tests/Feature/ProfileTest.php` are unmodified Breeze scaffolding and currently fail (register/email-verification/password-reset routes don't exist in this app's stripped-down `routes/auth.php`, and login is username+LDAP, not email+password) — left as-is deliberately, not a regression to chase; this app's actual login flow is out of scope for that scaffolding.
- Some routes intentionally call `ob_end_clean()` before streaming a file download (`/get_logs`, `/log-reader/read_logs`) — PHPUnit will mark tests hitting them as **risky** ("closed output buffers other than its own"), not failed. Expected, not a bug to fix.
- **`storage_path()` is not swapped out for tests the way DB/cache/queue/mail/session are** — it's the real, shared dev `storage/` tree, and (per the `make test` note above) tests run as **root** inside the container. Any test that writes under `storage_path()` and only cleans up in `beforeEach` (not `afterEach`) leaves root-owned files/directories behind after the suite finishes at whatever real paths that module also uses for actual requests — a later `www-data`-run web request that reads/writes the same path then gets a live "Permission denied", **unrelated to anything wrong with that request**. Confirmed live 2026-09-21: `RememberedConfig`'s single fixed-path `last-config.yml` (Authentik module) got clobbered root-owned by `RememberedConfigTest.php`'s last test, which then broke `GET /authentik` for real until fixed. Authentik's tests (`AuthentikControllerTest`, `RememberedConfigTest`, `Jobs/RunLogsFetchTest`) now pair every storage-touching `beforeEach` with a matching `afterEach`; this same risk is unaudited and likely still latent in Pangolin's tests (same shared-storage-tree pattern), just not yet triggered — a good first check if a similar "works in tests, breaks live" permissions error ever shows up there.

## Pangolin feature module

Integrates the `pangolin-utils` Python toolset (vendored as a git submodule at `pangolin-utils/`, upstream https://github.com/ktsouvalis/pangolin — its own `CLAUDE.md` documents the scripts/config schema/Integration API in depth, read it before touching anything here) behind a single menu entry and route (`/pangolin`, route name `pangolin.index`), one Blade page with 4 Alpine-driven tabs: Monitor, Logs, Import, Normalize. Built 2026-07-31, verified end-to-end against the live cluster (real dry-run Normalize returned live counts; real cluster HTTP checks and Newt SSH checks returned live statuses).

- **Monitor tab — native PHP, not a Python subprocess.** `monitor.py` is a Textual TUI with no headless/JSON mode, so its HTTP checks (pangolin/gerbil/keepalived/patroni/etcd/haproxy) and its Newt SSH reachability check were ported directly to `app/Services/Pangolin/ClusterMonitor.php` (HTTP via `Http` facade, SSH via `phpseclib3\Net\SSH2`). `app/Jobs/Pangolin/PollCluster.php` runs it and upserts `pangolin_monitor_statuses` (one row per service+node, latest-only, no history table by design); scheduled every minute in `routes/console.php` (`Schedule::job(new PollCluster)`). Both `developing/` and `production/` compose files now have a `scheduler` service (`while true; do php artisan schedule:run; sleep 60; done`) — dev originally didn't, so the every-minute poll silently never fired there until that service was added; the tab's "Refresh now" button (`PollCluster::dispatch()`) still works with neither. **`Schedule::job($job)` dispatches to the queue, it does not execute the job inline in the scheduler process** — the SSH check always actually runs in `queue-worker`, so `scheduler` never needs the SSH key secrets mounted (an earlier version of this compose setup mounted them there unnecessarily). The tab polls `GET pangolin/monitor/data` client-side every ~15s; no Reverb/broadcasting was added for this.
  - HAProxy status logic must mirror `monitor.py`'s `HAProxyPanel` exactly: a backend **pool** (e.g. `pangolin_primary`) is only unhealthy when it has **zero** UP servers — a Patroni-style pool with 1 UP out of 3 (or 2 of 3) is the *expected* steady state, not degraded. Flagging "any server down" instead of "any pool fully down" is a bug that was caught during verification (looked plausible, gave wrong status against the real cluster).
- **Logs / Import / Normalize tabs — shell out to the submodule.** `app/Services/Pangolin/ConfigYamlWriter.php` renders `config/pangolin.php` into the `config.yml` shape the scripts expect, written per-run to `storage/app/private/pangolin/runs/{id}/config.yml`; `app/Services/Pangolin/ScriptRunner.php` wraps Laravel's `Process` facade to run a script inside that per-run directory. Three jobs (`RunLogsFetch`, `RunImport`, `RunNormalize`) each own one `pangolin_runs` row (single table, `type` discriminator — logs/import/normalize share the exact same "queued external run with input/report/summary" shape, not three near-duplicate tables). `RunImport`/`RunNormalize` parse the resulting report xlsx directly via PhpSpreadsheet for status-count summaries rather than scraping stdout (`app/Jobs/Pangolin/Concerns/SummarizesXlsxReport.php`) — wrapped in try/catch so a parsing failure can't leave a run stuck at `running` with nothing recorded (this happened during verification: an uncaught exception there skipped the job's own final `update()` entirely).
  - PhpSpreadsheet in the installed version (3.x) has no `getCellByColumnAndRow` — use `getCell($columnLetter.$row)` (build the letter via `Coordinate::stringFromColumnIndex()`). `Cell::getValue()` isn't always a plain scalar (throws "Illegal offset type" if used as an array key un-cast) — cast to `(string)` first.
  - `normalize_private_resources.py --apply` prompts for interactive confirmation unless `--yes` or `--resource-id` is passed; since a subprocess has no stdin to answer that prompt, `RunNormalize` **always** passes `--yes` alongside `--apply` — the Laravel UI's own confirm checkbox is the actual human-confirmation step, not the script's prompt.
- **SSH keys: two config slots, currently the same physical key.** `PANGOLIN_SSH_KEY_PATH`/`PANGOLIN_SSH_KEY_HOST_PATH` (cluster nodes, used by `logs_viewer.py`'s `docker logs`/`journalctl` fetch) and `PANGOLIN_NEWT_SSH_KEY_PATH`/`PANGOLIN_NEWT_SSH_KEY_HOST_PATH` (Newt agent hosts, used by both that same script's Newt access-log fetch and the native `ClusterMonitor` SSH check) are kept as **separate** config/secret slots by design — different deployments could reasonably use different keys per group — but in this deployment both currently point at the same file: a passphrase-less "monitor LXC" key (comment `root@monitor`), authenticating as `root` against the Newt hosts and as `ktsouvalis` against the cluster nodes (confirmed by testing both usernames live — `root` failed against the cluster nodes, `ktsouvalis` worked). The user's own **passphrase-protected desktop key** was the original default for the cluster-node slot and reliably failed headlessly (`SSH error` on every call — `logs_viewer.py` treats that as non-fatal per-service, so the job still "completes" with an all-errors log, which is a trap when checking success naively) — don't reintroduce it there. If a future deployment needs genuinely different keys per group again, both slots already support that independently.
- **Config/credentials**: `config/pangolin.php` holds scalars via `env()` (API base_url/org_slug/api_key, VIP, SSH usernames/key paths) plus two things pulled from **JSON-encoded env vars** rather than hardcoded PHP arrays — `PANGOLIN_NODES_JSON` and `PANGOLIN_NEWT_HOSTS_JSON`. This isn't the usual `config/queue-monitor.php`-style mix of env+static-array: pangolin-utils' own convention treats real cluster IPs as sensitive (its `config.yml` is git-ignored entirely, unlike the tracked `config.yml.example`), so this app follows suit — real topology only ever lives in the git-ignored outer `.env`, never committed to `config/pangolin.php`. The `services:` list (which node group runs which docker/systemd unit, for `logs_viewer.py`) isn't sensitive the same way and is a plain committed array.
- **Access control**: `app/Http/Middleware/PangolinEnabled.php` checks `Menu::where('route_is', 'pangolin')->enabled` — the admin-only `auth()->user()->admin` check is present in the file but commented out, so in practice this currently allows *any* authenticated user whose menu is enabled, not just admins (Authentik's `AuthentikEnabled` was later built to deliberately match this same "menu-enabled only" behavior — see its own note below). The Menu row for this feature must have `route_is` set to the literal string `pangolin` (not `pangolin.index`), a deliberate choice made when wiring it up (means the nav-link "active" highlight in `navigation.blade.php`, which checks `request()->routeIs($menu->route_is)`, won't highlight on this page unless `route_is` is later changed to a wildcard like `pangolin.*` — a known, accepted cosmetic gap, not a bug).
- **etcd's v3 JSON gateway rejects an empty-array POST body.** `ClusterMonitor::checkEtcdNode()`'s `/v3/maintenance/status` call must send an actual empty JSON *object*, not `[]` — `Http::post($url, [])` serializes an empty PHP array as `[]`, which etcd's Go server rejects with "cannot unmarshal array into Go value of type map[string]json.RawMessage" (silently caught by the surrounding try/catch, so it looked like "leader/raft_term/db_kb just don't show up" rather than an obvious error). Fixed via `Http::withBody('{}', 'application/json')->post($url)`.
- **Monitor tab UI deliberately mimics `monitor.py`'s Textual TUI look** (dark GitHub-style palette `#0d1117`/`#161b22`/`#30363d`, colored status dots, one bordered panel per service) rather than a generic Blade/Tailwind table — built 2026-08-03 per explicit request to match the CLI tool's appearance. `pangolin/_monitor.blade.php` is a single Alpine component (`pangolinMonitor()`) fed the initial `$statuses` via `@js($statuses)` and re-fetching the same `pangolin/monitor/data` JSON on each 15s poll — panel logic (keepalived master election by highest `effective_priority` among `status === 'up'` nodes, pangolin/gerbil pairing by `node_ip`, etc.) lives once in that JS object, not duplicated between initial Blade render and poll-time JS. Only the Monitor tab escapes the page's `max-w-7xl` wrapper (full `w-full` width in `pangolin/index.blade.php`) so panels have room; the other three tabs stay constrained.
- **Postgres-direct checks and the `redis`/`postgres` config blocks are intentionally unported** — `monitor.py`'s Postgres direct-connect check isn't part of the documented panel set and isn't in `ClusterMonitor`; `logs_viewer.py`'s Newt CSV resolution needs direct Postgres reachability (port 5432) to resolve user/client/resource names and silently falls back to raw IPs/IDs if that's unreachable from wherever the job runs (confirmed during verification) — not a bug to chase, matches the script's own documented fallback behavior.
- **`storage/app/private/pangolin/` must stay `0777` on directories (files default `0644`; `config.yml` explicitly `0600`).** This tree is written by two different container users — the queue-worker/scheduler containers run their `php artisan queue:work`/`schedule:run` processes as **root** (no `USER` directive, no privilege drop), while the web container's Apache workers run as **www-data**. `0755` looks like the "obviously correct" tighter permission but is wrong here: it lets the non-owner read/traverse but not create new entries, which silently breaks whichever side didn't create a given directory first (queue-worker creates `runs/{id}/`, but the web process needs to read those files back for downloads; the web process creates `imports/`, which sits under a `pangolin/` parent that's usually root-owned because some job created it first). Root bypasses permission checks entirely, so `0777` on these internal, non-web-exposed directories is the actual fix, not a workaround to tighten later.
- **`romanzipp/laravel-queue-monitor` requires the `IsMonitored` trait per job class** — `monitor_queued_jobs => true` in its config only registers the listener, it does not auto-track every `ShouldQueue` job. `RunLogsFetch`/`RunImport`/`RunNormalize` use it (confirmed via a real `::dispatch()` through the actual queue, not a direct `handle()` call — the trait hooks `Queue::before`/`after` events that only fire for jobs actually processed off the queue). `PollCluster` deliberately does **not** use it — it fires every minute via the scheduler and would flood that table with a new row every 60s forever for no operational benefit.
- **Tab state (`x-data="{ tab: ... }"` in `pangolin/index.blade.php`) is synced to `?tab=` in the URL** two ways: server-side on load (`request('tab', 'monitor')`), and client-side via `x-init="$watch(...)"` calling `history.replaceState` whenever the Alpine `tab` value changes. Both are needed — the controller's own action methods (`logsFetch`, `resourcesImport`, `resourcesNormalize`) redirect to `route('pangolin.index', ['tab' => ...])` explicitly on success, but a **validation failure** redirects via Laravel's automatic `back()`, which follows the browser's `Referer` header — that header only has the right tab if the URL bar already had `?tab=` in it *before* the form was submitted, which is what the client-side sync guarantees.
- **`normalize_private_resources.py --resource-id` is numeric `siteResourceId` only** — but niceId is the only identifier users actually see (reports, the Pangolin dashboard). `App\Services\Pangolin\PangolinApiClient::resolveSiteResourceIds()` resolves non-numeric tokens against a live `GET /org/{org_slug}/site-resources` call (mirrors `get_site_resources()`/`api_headers()` in `normalize_private_resources.py` exactly — bearer token, `{data: {siteResources: [...], pagination: {...}}}` paginated shape) before `RunNormalize` builds `--resource-id` args. Confirmed live: resolved a real niceId to its numeric ID and got a correct scoped run back. `resolveSiteResourceIds()` silently drops any token that doesn't resolve (no error) — `RunNormalize` guards against the case where scoping was requested but every token failed to resolve (e.g. all mistyped) by failing the run instead of falling through to zero `--resource-id` args, which per `normalize_private_resources.py` would otherwise apply `--apply --yes` to *every* private resource in the org.
- **`accepted_if:apply,1` not `required_if:apply,1|accepted`** for the Normalize "confirm" checkbox. `accepted` (like `required`, `required_if`, `declined`) is one of Laravel's *implicit* rules — it runs even when the field is absent, independently of any other rule in the same pipe-separated list. Chaining it after `required_if` does not make it conditional; it always demanded the checkbox, including on plain dry runs. `accepted_if` is the actual conditional form.

## Authentik feature module

Behind a single menu entry and route (`/authentik`, route name `authentik.index`), one Blade page with **2** Alpine-driven tabs: Monitor and Logs. Removed the `authentik-utils` git submodule entirely on 2026-09-21 (no vendored Python source tree). The Logs tab shells out to `akropolis` (https://github.com/ktsouvalis/akropolis — a *different*, newer repo than the old `authentik-utils`/`akropolis-monitor`; a provisioning-and-monitoring toolkit whose `logs` subcommand is the only surface this app still depends on), fetched as a released single-file zipapp binary. **The Monitor tab went through two designs the same day before landing here**: first a pasted-config.yml-behind-a-browser-terminal approach (shelling to `akropolis monitor` via ttyd), replaced hours later with **native PHP polling** — no akropolis subprocess, no ttyd, no terminal-embedding infra at all for Monitor. The node IP / public Authentik URL / API token are **admin-editable settings persisted in the database** (`authentik_monitor_settings`, one row) instead of a per-run paste, so they're entered once and reused — this deployment is single-node (no Patroni/etcd/HAProxy/keepalived), so there was no real need to re-implement `akropolis monitor`'s full HA panel set, just its handful of single-node checks.

- **Monitor tab — same shape as Pangolin's ClusterMonitor/PollCluster, not a novel pattern.** `App\Services\Authentik\ClusterMonitor::run()` (reusing `App\Services\Concerns\ClusterMonitorHelpers`'s `row()` shape, shared with Pangolin's) fires 2 direct HTTP checks concurrently via `Http::pool()` against the configured node IP, plus 2 Authentik-API checks (Bearer token) against the configured public URL if a token is set:
  1. `authentik` — `GET https://{ip}/-/health/live/`, `withoutVerifying()` (no cert names the raw IP, same reasoning as the old 3-node port's `verify_tls: false`).
  2. `nginx` — `GET http://{ip}:8080/nginx_status`, parsed the same way as Pangolin's/the old Authentik `ClusterMonitor`'s nginx status parsing (active/reading/writing/waiting via regex).
  3. `workers` — `GET {url}/api/v3/tasks/workers/` (Bearer token) — which workers are connected via the broker heartbeat. `unknown` (not `down`) when no token is configured — there's a real difference between "not configured" and "checked and failed".
  4. `worker_queue` — `GET {url}/api/v3/tasks/tasks/status/` (Bearer token) — background task health (email, outpost sync, policy cache...); `degraded` on any rejected/warning count, `down` on any error count, matching the old 3-node port's exact thresholds.
  **There is deliberately no direct worker-liveness port check** (`GET http://{ip}:9081/`) — an earlier version of this file probed one, modeled on the real pasted `config.<site>.monitor.yml` this module was built from (which lists a separate `authentik_worker: 9081` port). Confirmed live it doesn't actually work for this deployment — the port has nothing answering behind it, so the row just sat permanently red regardless of the worker's real health, a false positive rather than a real one. Removed entirely rather than "fixed": the `workers` API check above is the *better* signal anyway (a liveness port can stay green even when the dramatiq consumer itself is dead — this deployment just never exposed one to check).
  Ports (443/8080) are fixed in `config/authentik.php`'s `monitor.ports` — not admin-editable, since they're this specific single-node deployment's actual listener ports, not something that varies per poll.
  `App\Jobs\Authentik\PollCluster` runs it and upserts `authentik_monitor_statuses` (one row per service, latest-only — re-created via a fresh migration, `2026_09_21_120731_create_authentik_monitor_statuses_table.php`, after an earlier same-day migration had dropped the original table when the ttyd-terminal design briefly removed polling entirely); scheduled every minute in `routes/console.php`. The tab polls `GET authentik/monitor/data` client-side every ~15s, `authentik/_monitor.blade.php` — same dark GitHub-style panel look as Pangolin's/the original Authentik monitor tab, just one panel instead of several per-node ones (single node).
- **`App\Models\AuthentikMonitorSettings` — one DB row, edited inline at the top of the Monitor tab.** `node_ip`/`authentik_url`/`api_token` — `api_token` encrypted at rest via `Crypt::encryptString()`, same convention as `Chatbot::api_key` (see `ChatbotController`), not an `encrypted` cast. The edit form's token field is **never pre-filled with the decrypted value** — leaving it blank on save means "keep the current token", the only way to distinguish that from "clear it" given the field can't safely show what's already stored; `AuthentikController::monitorSettingsUpdate()` only touches `api_token` when `$request->filled('api_token')`. Saving settings also re-dispatches `PollCluster` immediately, so the dashboard doesn't sit on stale/no data until the next scheduled minute.
  - **Tests hitting `monitor.settings.update` without `Queue::fake()` make real network calls** — caught live: one test took 5s (matching `http_timeout`) because `monitorSettingsUpdate()`'s re-poll ran for real under `QUEUE_CONNECTION=sync`, actually hitting the production Authentik cluster. Every test that POSTs there and expects success now calls `Queue::fake()` first; a test that only checks a validation failure doesn't need it (validation fails before `PollCluster::dispatch()` is ever reached).
- **Verified against the real production cluster, not just `Http::fake()`** — using the real node IP/URL/API token, a real poll returned real data (1 worker connected, real task-queue counts — including a real `rejected` count worth investigating operationally, unrelated to this app) confirming the token's permissions and endpoint shapes are correct.
- **Logs tab is unchanged by the Monitor rewrite** — still shells out to `akropolis logs config.yml --save cluster_logs [--last H] [--level L]` (`CONFIG` positional, not the old akropolis-monitor's `--config` flag) via `app/Services/Authentik/ScriptRunner.php`. The user still pastes `config.<site>.monitor.yml` contents into a plain `<textarea>` per fetch (not a file upload — changed from upload to paste same day as the terminal-embedding attempt, before that was itself replaced for Monitor) — `AuthentikController::logsFetch()` validates it's syntactically valid YAML (`Symfony\Component\Yaml\Yaml::parse()`, catching `ParseException` — a pasted textarea has no filename/extension to sanity-check the way an upload did) and `file_put_contents()`s it into `storage/app/private/authentik/runs/{id}/config.yml` **before** dispatching `RunLogsFetch` (the old `ConfigYamlWriter` that used to render this from env/config is deleted). `App\Services\Authentik\RememberedConfig` persists the last Logs paste to `storage/app/private/authentik/last-config.yml` (0600) so re-fetching doesn't mean re-pasting — Logs-only now (Monitor doesn't paste a config at all anymore).
- **`mkdir($dir, 0777, true)` alone does not reliably produce 0777** — its mode argument is masked by the calling process's umask, exactly like the POSIX `mkdir()` syscall it wraps (Apache's www-data worker here inherits umask `0022`), so every raw `mkdir(..., 0777, true)` call in this module (and, unaudited, likely elsewhere — e.g. Pangolin's identical pattern) was silently creating `0755` directories instead. Harmless until a *different* uid needs to write into the same tree, which is exactly `storage/app/private/authentik/runs/` (web process vs. queue-worker): found live when a real browser request (www-data) hit `mkdir(): Permission denied` on a `0755` directory left behind by root-run manual testing. Fixed via `App\Services\Concerns\EnsuresWritableDirectory` (a small trait, used by `RunLogsFetch` and `AuthentikController`) — its `ensureWritableDirectory()` always `chmod()`s a directory it just created, and best-effort `chmod()`s (wrapped in try/catch — a `chmod()` on a directory we don't own throws an `ErrorException` under this app's default error handling) one that already exists but isn't writable, without letting that failure fail the request. A pre-existing permissions problem from outside this request can't always be self-healed this way — the one-time live fix was `docker compose exec application bash -c 'find storage/app/private/authentik -type d -exec chmod 0777 {} \;'`.
- **`storage_path()` is the real, shared dev storage tree — not swapped out for tests — and `make test` runs as root.** A test that writes there and only cleans up in `beforeEach` (not `afterEach`) leaves root-owned residue after the suite finishes, at paths this module also uses for real requests; a later `www-data` request then gets a live permission error unrelated to anything wrong with it. Confirmed live: `RememberedConfig`'s single fixed-path `last-config.yml` got clobbered root-owned by a test, breaking `GET /authentik` for real. Every Authentik test file that touches `storage_path()` now pairs `beforeEach` with `afterEach`.
- **`storage/app/private/authentik/` keeps the same `0777`-on-directories treatment as `storage/app/private/pangolin/`** — see the Pangolin section above for the full cross-uid rationale.
- **Access control unchanged**: `app/Http/Middleware/AuthentikEnabled.php` still checks `Menu::where('route_is', 'authentik')->enabled` only, no `admin`-only gate (mirrors Pangolin's current behavior). Same `route_is` = literal `authentik` (not `authentik.index`) cosmetic nav-highlight gap as Pangolin's.
- **Runbook: bumping to a new `akropolis` release.** Pinned by version + sha256 `ARG`s in **both** `developing/Dockerfile` and `production/Dockerfile` (two separate files in the outer `containers-files-per-projects` infra repo) — no submodule, so there's only the one pin location.
  1. `gh release list --repo ktsouvalis/akropolis` to see what's newer; read release notes for anything touching the `logs` subcommand's args or the `config.<site>.monitor.yml` schema (the only surface this app depends on now — `monitor` isn't used at all).
  2. Download the asset yourself and `sha256sum` it rather than trusting the published `SHA256SUMS` text verbatim — hashing an independently-downloaded copy is what actually catches a swapped asset.
  3. Update the version/sha256 `ARG`s in both Dockerfiles.
  4. Test in dev: rebuild (`docker compose build application`), recreate `application`/`queue-worker`, run `make test ARGS="--filter=Authentik"`, and manually run a Logs fetch once.
  5. Commit+push the outer `containers-files-per-projects` repo (both Dockerfiles).
  6. Deploy to prod: `~/dgu-prod` on the prod host is **not** git-tracked for the infra files, so `production/Dockerfile` has to be copied over by hand (`scp`) — diff the live file against the repo copy first, since it can drift independently. Then SSH in and run `make update`.
  A `pangolin-utils` release still follows the old submodule+venv path (`make update-subrepos` or a manual submodule bump, then a normal rebuild) — see the Pangolin section above; that module didn't change.

## Sheetmailers feature module

Send a stored subject/body/signature template to a recipient list built from an uploaded xlsx or a pasted comma list, via a 4-step flow (Create → Edit content+recipients → Confirm → Send). Reworked 2026-08-07 (bug fixes, then two follow-up feature passes) — see `tests/Feature/Sheetmailers/SheetmailerTest.php` for the full behavioral spec.

- **Sending is async via `Bus::batch()`, not a per-recipient `Mail::queue()` loop.** `SheetmailerController::send()` builds one `App\Jobs\Sheetmailers\SendSheetmailerEmail` per recipient (each does a synchronous `Mail::to($email)->send(new MailSheetMailer(...))` inside its own `handle()`), dispatches them all as a single named batch (`sheetmailer-{id}`) with `->allowFailures()` (default batch behavior *cancels remaining jobs on the first failure*, which would silently stop the rest of a send over one bad address), and stores `$batch->id` in session keyed per-sheetmailer. **`MailSheetMailer` itself is no longer `ShouldQueue`/`IsMonitored`** — the wrapper job is what's actually queued and monitored; calling `Mail::to()->queue($mailSheetMailer)` again would silently double-dispatch if this is ever touched.
- **Live progress bar** on the Edit page (`sheetmailers/_send-progress.blade.php`, Alpine, same `fetch()`-polling-every-N-seconds pattern as Pangolin's `pangolinMonitor()`) polls `GET sheetmailers/{id}/send-status/{batch}` (`SheetmailerController::sendStatus()`), which resolves the batch via `Bus::findBatch()` and is scoped so a batch id only resolves for the sheetmailer whose session actually stored it — a guessed/reused id 404s even if it's a real batch for a *different* sheetmailer. The Edit page (`activeSendBatchSummary()`) self-clears the stored batch id once `$batch->finished()` is true, so a later page load doesn't show a stale "done" bar; a tab left open mid-send still sees the final state once via its last poll before that happens.
- **Recipient email shows in `/jobs` via two separate mechanisms, not one — because `QUEUE_CONNECTION=sync` never fires `JobQueued`.** `romanzipp/laravel-queue-monitor`'s `initialMonitorData()` hook (which `SendSheetmailerEmail` implements, returning `['recipient' => $email]`) is only read from the `JobQueued` event — real queue drivers (`database`, `redis`) fire it when a job is pushed, but `SyncQueue::push()` calls `executeJob()` directly and never fires `JobQueued` at all, so under `sync` (tests, or if `QUEUE_CONNECTION=sync` anywhere) the row exists (created later at `JobProcessing`) but starts with empty `data`. `SendSheetmailerEmail::handle()` therefore *also* calls `$this->queueData(['recipient' => $email], merge: true)` as the first line — driver-agnostic, since it looks up the monitor row that's guaranteed to exist by the time `handle()` runs. Needed `config('queue-monitor.ui.show_custom_data')` flipped to `true` (was `false`) for the column to actually render.
- **Staged recipients (from upload/paste) live in session under `sheetmailers.recipients.{id}`, not a flat key** — namespaced per sheetmailer specifically so uploading a list for sheetmailer A (e.g. a second browser tab) can't leak into sheetmailer B's Confirm/Send if you navigate directly to B's `/confirm` URL. `confirm()`/`preview`-successor/`send()` all guard on this being empty and redirect back to Edit with a flash error instead of the old behavior of indexing into a null/missing array.
- **The Confirm page's "Send" form lets the user uncheck individual recipients before sending** (`keep[]` checkboxes + a `keep_present` hidden sentinel field). `send()` only applies the `keep` filter when `keep_present` is present — that sentinel disambiguates "form was submitted with everything unchecked" (empty `keep[]`, which browsers omit entirely for unchecked boxes — this must send *nothing* and redirect back to Confirm with an error) from "some other/older caller posted here without any selection concept at all" (no `keep_present` key — this must fall through to sending the full staged list, not silently send zero).
- **There is no Preview route anymore** (removed 2026-08-07) — the Confirm page's "What will be sent" panel (email-preview-styled card: From/Subject header, body, signature) replaced it inline, so there's no second page/tab needed to sanity-check content before sending. `MailSheetMailer`'s `$username` constructor param was removed along with it (it only ever existed to flip a `$username == 'preview'` branch in `sheetmailers/mail.blade.php`, which no longer exists).
- `sheetmailers/_steps.blade.php` is a shared 3-step indicator (`@include`d with `['step' => 1|2|3]`) across Create (index.blade.php's create card), Edit, and Confirm.
- The two recipient-entry forms (upload xlsx vs. paste comma list) on Edit are Alpine tabs (`x-data="{ recipientTab: 'file' }"`), not two stacked `<form>`s separated by `<hr>` — each tab's `<form>` keeps its own `required` field; hiding the inactive one via `x-show` doesn't affect the visible one's native validation since they're separate forms.
- **`Route::resource('/sheetmailers', ...)` is scoped with `->only(['index','store','edit','update','destroy'])`** — the controller has no `create()`/`show()` methods, so the unscoped default previously left `GET /sheetmailers/create` and `GET /sheetmailers/{id}` wired to routes that would fatal (call to undefined method) if hit. Both URIs are the same single-segment shape as `update`/`destroy`'s `PUT|PATCH|DELETE /sheetmailers/{id}`, so hitting them with GET now correctly 405s (method not registered for that URI) rather than 404ing — don't "fix" a test expecting 404 there.
- Email-splitting logic (regex/`filter_var` validation, eligible vs. invalid) lives once in `App\Services\Sheetmailers\RecipientListParser` (`fromWorksheet()` / `fromCommaList()`), shared by `upload_file` and `comma_mails` — previously duplicated inline in both controller methods.

## Mailers ("DFD" — mail-to-department) feature module

Upload files (Mailer model, table `mail_to_departments`) whose filenames are matched by a numeric prefix (`\d{3}` or `\d{4}` at the start, e.g. `501 - report.pdf`) to a `Department` row by id, then mail each matched file to that department's address, via a 3-step flow (Create → Add files → Review & send). Brought up to the same standard as the Sheetmailers rework on 2026-08-07, since it's the same shape (`Route::resource` + extra action routes, session-staged data, a per-recipient send loop) and had several of the exact same bugs.

- **`Route::resource('/mailers', ...)` is scoped with `->only(['index','store','edit','update','destroy'])`**, same reasoning as Sheetmailers' — `MailerController` has no `create()`/`show()` methods, so the unscoped default left `GET /mailers/create` and `GET /mailers/{id}` wired to routes that would fatal if hit.
- **Sending is async via `Bus::batch()` for `send_all()`, one job (`App\Jobs\Mailers\SendMailerFile`) per department**, dispatched with `->allowFailures()` so one department's mail failing doesn't cancel the rest — mirrors `App\Jobs\Sheetmailers\SendSheetmailerEmail`. The single-department `send()` action (per-row "Send" button on Review) dispatches the same job directly, no batch needed for one recipient. **`MailToDepartment` itself is no longer `ShouldQueue`/`IsMonitored`** — the job is what's actually queued and monitored, same split as `MailSheetMailer`/`SendSheetmailerEmail`. Its unused `$username` constructor param (never read by `mailers/mail.blade.php`) was also dropped.
- **Live progress bar** on the Review page (`mailers/_send-progress.blade.php`, same Alpine polling pattern as `sheetmailers/_send-progress.blade.php`) polls `GET mailers/{mailer}/send-status/{batch}` (`MailerController::sendStatus()`), scoped so a batch id only resolves for the mailer whose session actually stored it.
- **Department/filename shows in `/jobs` via `SendMailerFile::initialMonitorData()`/`queueData()`** (`['department' => ..., 'file' => ...]`), same belt-and-braces double-set as `SendSheetmailerEmail` so it works whether or not `QUEUE_CONNECTION=sync` fired `JobQueued`. Uses the same already-flipped `config('queue-monitor.ui.show_custom_data')`.
- **`review()`'s department-match list lives in session under `mailers.review.{id}`, not a flat `review_array` key** — namespaced per mailer for the same reason Sheetmailers' recipient staging is namespaced: reviewing mailer A in one tab and mailer B in another, then submitting "Send All" from a stale tab, must not send mailer B's matches under mailer A's context. `send_all()` reads from this session key (populated by visiting `review()` first) rather than recomputing, so it also guards against a `send_all` POST with nothing staged (flashes a warning instead of silently no-op'ing).
- **`review()` guards against a files-less mailer** (`$mailer->files` null/empty) with a redirect back to Edit and a flash error, instead of the previous crash (`foreach` on `null`, and `$review_array` was never initialized before the loop when reachable).

- **Malformed mail markup fix**: `mailers/mail.blade.php` used to wrap the rich-text `$body` in `<p>{!! $body !!}</p>`, nesting the editor's own block tags (`<p>`, `<ul>`, `<li>`, ...) inside a `<p>` — same bug class fixed in `sheetmailers/mail.blade.php`, fixed the same way (plain `<div>`).
- `mailers/_steps.blade.php` is the same shared step-indicator pattern as Sheetmailers' (`@include`d with `['step' => 1|2|3]`), across Create (index.blade.php's create card), Edit, and Review — its steps are Name → Add files → Review & send (Mailers has no separate recipient-entry step; files *are* the recipients, matched by filename).
- Index gained pagination (`paginate(15)`) and a human "Created" column (`created_at->diffForHumans()`), same as Sheetmailers' index.

## Items feature module

Tracks physical inventory (`Item` model, table `items`) with per-item file attachments (PDFs), owner assignment, a "given away" flag, and a "Αποθήκη ΜΨΔ" (local storage) flag, plus an xlsx export of everything not given away. Brought up to the same standard as Mailers/Sheetmailers on 2026-08-07, but **its index page deliberately did not get server-side pagination** — see below, that's the one place this module intentionally diverges from the other two.

- **`resources/views/items/index.blade.php`'s `#DataTable` is a client-side DataTables.js instance** (`resources/js/items/datatable_init.js`), not a plain Blade table — it renders the whole list into the DOM and does its own paging (`lengthMenu`/`pageLength: 50`) plus a custom per-column include/exclude regex search (two inputs injected into each filterable `<th>`, wired in that same JS file). Because of this, `ItemController::index()` still calls **`Item::all()`, not `->paginate()`** — server-side pagination was tried during the 2026-08-07 rework and reverted, since DataTables would then only ever see one page's worth of rows in the DOM, silently breaking include/exclude search for everything outside the current page. If this list ever grows large enough that shipping the full table to the browser becomes a real problem, the correct fix is wiring DataTables' `serverSide: true` mode against a new JSON endpoint (paging/search/sort done in the SQL query) — not `Item::paginate()` — since that's the only way to keep both a small payload and full-list search.
- **DataTables' stock theme is restyled in `resources/css/app.css`** (`div.dt-container ...` rules, pill-shaped `.dt-paging-button`s, blue-600 current page, etc.) to match the app's Tailwind look rather than the default DataTables theme — added 2026-08-07 alongside the pagination investigation above. Scoped by DataTables' own generated class names (`dt-container`/`dt-paging`/`dt-length`/`dt-info`), safe app-wide since Items is currently the only page using DataTables.
- **`Route::resource('/items', ItemController::class)` is scoped with `->except(['show'])`**, not `->only([...])` like Mailers/Sheetmailers — unlike those two, `ItemController` *does* have a real `create()`/`create.blade.php` (a dedicated page, not an inline form), so `create` needed to stay registered; only `show` was dead (no `show()` method, would fatal if `GET /items/{item}` were ever hit).
- **File upload/move/delete logic lives once in `App\Services\Items\ItemFileManager`**, shared by `store()`, `update()`, `download_file()`, `destroy()`, and `delete_file()` — previously the unique-name-generate → `move()` → metadata-append block was duplicated verbatim between `store()` and `update()`, same bug class the Sheetmailers rework fixed by extracting `RecipientListParser`.
- **`file_path.*` validation now pairs `mimes:pdf` with `mimetypes:application/pdf`**, mirroring the `mimes`+`mimetypes` pairing `SheetmailerController::upload_file()` already used for its xlsx uploads (`mimes` mostly reflects the extension, `mimetypes` checks the actual detected content type — pairing them means a renamed file can't sneak past either check alone).
- **`extract()`'s xlsx report writes into `storage/app/private/items/exports/`, a separate subdirectory from real item file uploads** (which live directly under `storage/app/private/items/`), and now calls `->deleteFileAfterSend()` — previously it wrote straight into the uploads directory with no cleanup, so reports accumulated forever and a same-day re-export silently clobbered the previous one. Also switched its `Gate::authorize()` from `'create'` to `'viewAny'`, since it's a read-only export, not a mutation — same category of Gate/action mismatch corrected in the Mailers/Sheetmailers reworks (there it was view→update for mutating actions; here it's the reverse direction, create→viewAny for a non-mutating one).
- **`update()` guards `$incoming['user_id']` with `?? null`** before comparing to the sentinel value `99` (which the "Assigned To" select uses to mean "unassigned", see `items/edit.blade.php`) — `$incoming = $request->except('file_path')` only contains keys actually present in the request, so a malformed POST missing `user_id` entirely used to trigger a PHP "undefined array key" warning rather than a clean null-coalesce.
