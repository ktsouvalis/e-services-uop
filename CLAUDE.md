# CLAUDE.md

Guidance for working in this repo.

## What this is

A Laravel 11 (PHP 8.2) internal admin/tools app ("e-services") for a university's Digital Governance Unit. Breeze-based auth, MySQL, database-backed queue/cache/session, Vite + Tailwind frontend, Blade views (no SPA framework). Multiple unrelated internal tools live side by side in one app, each gated by a DB-driven, toggleable menu system.

## Stack

- Laravel 11, PHP 8.2, Breeze scaffolding (`laravel/breeze` dev dep, `routes/auth.php`).
- DB: MySQL (`DB_CONNECTION=mysql`). Queue/cache/session all use the `database` driver.
- `romanzipp/laravel-queue-monitor` — job run tracking + a built-in UI at `/jobs` (see `config/queue-monitor.php`; `ui.enabled` true, prefix `jobs`).
- `phpoffice/phpspreadsheet` — used repeatedly for xlsx read/write (see `LogReaderController`, `ItemController`). Already a first-class way to handle spreadsheet import/export in this app, not a bolt-on.
- `directorytree/ldaprecord-laravel`, `laravel/reverb` (websockets, used for the chat feature — `App\Events\MessageSent`), `clue/redis-react`, `openai-php/client` (used by the Chatbot/AImodel features).
- Frontend: Blade + Alpine (via Breeze), Tailwind, Vite. No Livewire/Inertia present.

## Feature-module pattern (important — follow this for new features)

Every feature area (Mailers, Sheetmailers, Items, Chatbots, Notifications, Menus, Log-reader...) follows the same shape:

1. **Migration** for its own table(s).
2. **Model** (`app/Models/X.php`) — typically `protected $guarded = ['id']`.
3. **Policy** (`app/Policies/XPolicy.php`) gating `viewAny`/`create`/`update`/`delete` — for most features the policy checks `Menu::where('route_is', $this->menu)->first()->enabled` (a hardcoded `route_is` string set as a property on the policy) **and** `auth()->check()`, i.e. authorization is menu-driven, not role-driven, except where `auth()->user()->admin` is checked directly (e.g. the `/get_logs` route in `routes/web.php`).
4. **Gate registration**: only *some* policies are wired in `app/Providers/AppServiceProvider.php` (`Gate::policy(...)`) — others rely on Laravel's auto-discovery convention (`XPolicy` next to `X` model). Check both before assuming a policy isn't registered.
5. **Controller** — resourceful (`Route::resource`) plus extra `Route::group(['prefix' => 'x', 'middleware' => 'auth'], ...)` routes for non-CRUD actions (upload, download, send, toggle, etc). Controllers call `Gate::authorize(...)` per action rather than relying on middleware alone.
6. **Routes** all declared in `routes/web.php` (no route files per feature, no API routes — this is a server-rendered app only).
7. **Views** under `resources/views/{feature}/`.
8. **Logging**: features log to their own named channel, e.g. `Log::channel('menus')->info(...)`, `Log::channel('log-reader')->error(...)` — check `config/logging.php` for configured channels before adding a new one.
9. **File storage**: uploads go to `storage/app/private/{feature}/` (Laravel 11's default private disk root), accessed via `storage_path("app/private/{feature}/...")`, not the `Storage` facade's public disk. Files are often processed then immediately downloaded via `response()->download(...)->deleteFileAfterSend()`.

## Menu system (drives both navigation and access)

- `menus` table: `title`, `route` (route name to link to), `route_is` (route-name pattern used for both nav "active" highlighting **and** as the policy's authorization key), `enabled` (bool toggle).
- Rendered in `resources/views/layouts/navigation.blade.php` via `@foreach(App\Models\Menu::all() as $menu)` — skips disabled menus. **Menus are pure DB rows, not config/seeders** — adding a nav item for a new feature means inserting a `menus` row (via the `/menus` UI itself, which is behind `MenuPolicy`), not editing a blade file.
- A menu being disabled doesn't just hide the nav link — policies actively check `enabled` and deny access even via direct URL. Some features additionally gate an entire route group behind a small dedicated middleware that re-checks the same thing (see `App\Http\Middleware\LogReaderEnabled`, applied to the `log-reader` route group) — use that pattern when a route group (not a resourceful controller with Gate calls) needs the same "disabled in menu ⇒ 403" behavior.
- `MenuController::toggleEnabled` (`POST /menus/toggle-enabled/{menu}`) is the AJAX endpoint the UI uses to flip `enabled` without a full page reload.

## Auth / users

- `App\Models\User` has a plain `admin` boolean column (`2024_10_17_083949_add_admin_to_users_table.php`), checked directly with `auth()->user()->admin` in a few places (the `/get_logs` zip-download route) rather than through a policy/gate. Not every admin-only action goes through the Menu/Policy system — some just inline-check this flag.
- No roles/permissions package (no spatie/permission etc.) — authorization is entirely: Breeze session auth + the `admin` boolean + the Menu-driven policies described above.

## Routes of note (`routes/web.php`)

- `/health` — plain JSON `{"status":"OK"}`, unauthenticated (liveness probe).
- `/get_logs?date=YYYY-MM-DD` — admin-only, zips and downloads `storage/logs/*<date>.log` files.
- `/log-reader` — regex-based log line extractor over an uploaded file, outputs an xlsx of unique matches; gated by `LogReaderEnabled` middleware (menu-driven) rather than a policy.
- Chat feature (`/chat/send-message`) broadcasts via Reverb (`App\Events\MessageSent`) — this app has real-time infra already wired (Reverb + Echo), reusable for any future "live updating" UI instead of polling.

## Pangolin feature module

Integrates the `pangolin-utils` Python toolset (vendored as a git submodule at `pangolin-utils/`, upstream https://github.com/ktsouvalis/pangolin — its own `CLAUDE.md` documents the scripts/config schema/Integration API in depth, read it before touching anything here) behind a single menu entry and route (`/pangolin`, route name `pangolin.index`), one Blade page with 4 Alpine-driven tabs: Monitor, Logs, Import, Normalize. Built 2026-07-31, verified end-to-end against the live cluster (real dry-run Normalize returned live counts; real cluster HTTP checks and Newt SSH checks returned live statuses).

- **Monitor tab — native PHP, not a Python subprocess.** `monitor.py` is a Textual TUI with no headless/JSON mode, so its HTTP checks (pangolin/gerbil/keepalived/patroni/etcd/haproxy) and its Newt SSH reachability check were ported directly to `app/Services/Pangolin/ClusterMonitor.php` (HTTP via `Http` facade, SSH via `phpseclib3\Net\SSH2`). `app/Jobs/Pangolin/PollCluster.php` runs it and upserts `pangolin_monitor_statuses` (one row per service+node, latest-only, no history table by design); scheduled every minute in `routes/console.php` (`Schedule::job(new PollCluster)`). Both `developing/` and `production/` compose files now have a `scheduler` service (`while true; do php artisan schedule:run; sleep 60; done`) — dev originally didn't, so the every-minute poll silently never fired there until that service was added; the tab's "Refresh now" button (`PollCluster::dispatch()`) still works with neither. **`Schedule::job($job)` dispatches to the queue, it does not execute the job inline in the scheduler process** — the SSH check always actually runs in `queue-worker`, so `scheduler` never needs the SSH key secrets mounted (an earlier version of this compose setup mounted them there unnecessarily). The tab polls `GET pangolin/monitor/data` client-side every ~15s; no Reverb/broadcasting was added for this.
  - HAProxy status logic must mirror `monitor.py`'s `HAProxyPanel` exactly: a backend **pool** (e.g. `pangolin_primary`) is only unhealthy when it has **zero** UP servers — a Patroni-style pool with 1 UP out of 3 (or 2 of 3) is the *expected* steady state, not degraded. Flagging "any server down" instead of "any pool fully down" is a bug that was caught during verification (looked plausible, gave wrong status against the real cluster).
- **Logs / Import / Normalize tabs — shell out to the submodule.** `app/Services/Pangolin/ConfigYamlWriter.php` renders `config/pangolin.php` into the `config.yml` shape the scripts expect, written per-run to `storage/app/private/pangolin/runs/{id}/config.yml`; `app/Services/Pangolin/ScriptRunner.php` wraps Laravel's `Process` facade to run a script inside that per-run directory. Three jobs (`RunLogsFetch`, `RunImport`, `RunNormalize`) each own one `pangolin_runs` row (single table, `type` discriminator — logs/import/normalize share the exact same "queued external run with input/report/summary" shape, not three near-duplicate tables). `RunImport`/`RunNormalize` parse the resulting report xlsx directly via PhpSpreadsheet for status-count summaries rather than scraping stdout (`app/Jobs/Pangolin/Concerns/SummarizesXlsxReport.php`) — wrapped in try/catch so a parsing failure can't leave a run stuck at `running` with nothing recorded (this happened during verification: an uncaught exception there skipped the job's own final `update()` entirely).
  - PhpSpreadsheet in the installed version (3.x) has no `getCellByColumnAndRow` — use `getCell($columnLetter.$row)` (build the letter via `Coordinate::stringFromColumnIndex()`). `Cell::getValue()` isn't always a plain scalar (throws "Illegal offset type" if used as an array key un-cast) — cast to `(string)` first.
  - `normalize_private_resources.py --apply` prompts for interactive confirmation unless `--yes` or `--resource-id` is passed; since a subprocess has no stdin to answer that prompt, `RunNormalize` **always** passes `--yes` alongside `--apply` — the Laravel UI's own confirm checkbox is the actual human-confirmation step, not the script's prompt.
- **SSH keys: two config slots, currently the same physical key.** `PANGOLIN_SSH_KEY_PATH`/`PANGOLIN_SSH_KEY_HOST_PATH` (cluster nodes, used by `logs_viewer.py`'s `docker logs`/`journalctl` fetch) and `PANGOLIN_NEWT_SSH_KEY_PATH`/`PANGOLIN_NEWT_SSH_KEY_HOST_PATH` (Newt agent hosts, used by both that same script's Newt access-log fetch and the native `ClusterMonitor` SSH check) are kept as **separate** config/secret slots by design — different deployments could reasonably use different keys per group — but in this deployment both currently point at the same file: a passphrase-less "monitor LXC" key (comment `root@monitor`), authenticating as `root` against the Newt hosts and as `ktsouvalis` against the cluster nodes (confirmed by testing both usernames live — `root` failed against the cluster nodes, `ktsouvalis` worked). The user's own **passphrase-protected desktop key** was the original default for the cluster-node slot and reliably failed headlessly (`SSH error` on every call — `logs_viewer.py` treats that as non-fatal per-service, so the job still "completes" with an all-errors log, which is a trap when checking success naively) — don't reintroduce it there. If a future deployment needs genuinely different keys per group again, both slots already support that independently.
- **Config/credentials**: `config/pangolin.php` holds scalars via `env()` (API base_url/org_slug/api_key, VIP, SSH usernames/key paths) plus two things pulled from **JSON-encoded env vars** rather than hardcoded PHP arrays — `PANGOLIN_NODES_JSON` and `PANGOLIN_NEWT_HOSTS_JSON`. This isn't the usual `config/queue-monitor.php`-style mix of env+static-array: pangolin-utils' own convention treats real cluster IPs as sensitive (its `config.yml` is git-ignored entirely, unlike the tracked `config.yml.example`), so this app follows suit — real topology only ever lives in the git-ignored outer `.env`, never committed to `config/pangolin.php`. The `services:` list (which node group runs which docker/systemd unit, for `logs_viewer.py`) isn't sensitive the same way and is a plain committed array.
- **Access control**: `app/Http/Middleware/PangolinEnabled.php` requires `auth()->user()->admin` (same bar as this app's existing `/get_logs` admin-only route — these tools can grant live network access) **and** `Menu::where('route_is', 'pangolin')->enabled` — the Menu row for this feature must have `route_is` set to the literal string `pangolin` (not `pangolin.index`), a deliberate choice made when wiring it up (means the nav-link "active" highlight in `navigation.blade.php`, which checks `request()->routeIs($menu->route_is)`, won't highlight on this page unless `route_is` is later changed to a wildcard like `pangolin.*` — a known, accepted cosmetic gap, not a bug).
- **etcd's v3 JSON gateway rejects an empty-array POST body.** `ClusterMonitor::checkEtcdNode()`'s `/v3/maintenance/status` call must send an actual empty JSON *object*, not `[]` — `Http::post($url, [])` serializes an empty PHP array as `[]`, which etcd's Go server rejects with "cannot unmarshal array into Go value of type map[string]json.RawMessage" (silently caught by the surrounding try/catch, so it looked like "leader/raft_term/db_kb just don't show up" rather than an obvious error). Fixed via `Http::withBody('{}', 'application/json')->post($url)`.
- **Monitor tab UI deliberately mimics `monitor.py`'s Textual TUI look** (dark GitHub-style palette `#0d1117`/`#161b22`/`#30363d`, colored status dots, one bordered panel per service) rather than a generic Blade/Tailwind table — built 2026-08-03 per explicit request to match the CLI tool's appearance. `pangolin/_monitor.blade.php` is a single Alpine component (`pangolinMonitor()`) fed the initial `$statuses` via `@js($statuses)` and re-fetching the same `pangolin/monitor/data` JSON on each 15s poll — panel logic (keepalived master election by highest `effective_priority` among `status === 'up'` nodes, pangolin/gerbil pairing by `node_ip`, etc.) lives once in that JS object, not duplicated between initial Blade render and poll-time JS. Only the Monitor tab escapes the page's `max-w-7xl` wrapper (full `w-full` width in `pangolin/index.blade.php`) so panels have room; the other three tabs stay constrained.
- **Postgres-direct checks and the `redis`/`postgres` config blocks are intentionally unported** — `monitor.py`'s Postgres direct-connect check isn't part of the documented panel set and isn't in `ClusterMonitor`; `logs_viewer.py`'s Newt CSV resolution needs direct Postgres reachability (port 5432) to resolve user/client/resource names and silently falls back to raw IPs/IDs if that's unreachable from wherever the job runs (confirmed during verification) — not a bug to chase, matches the script's own documented fallback behavior.
- **`storage/app/private/pangolin/` must stay `0777` on directories (files default `0644`; `config.yml` explicitly `0600`).** This tree is written by two different container users — the queue-worker/scheduler containers run their `php artisan queue:work`/`schedule:run` processes as **root** (no `USER` directive, no privilege drop), while the web container's Apache workers run as **www-data**. `0755` looks like the "obviously correct" tighter permission but is wrong here: it lets the non-owner read/traverse but not create new entries, which silently breaks whichever side didn't create a given directory first (queue-worker creates `runs/{id}/`, but the web process needs to read those files back for downloads; the web process creates `imports/`, which sits under a `pangolin/` parent that's usually root-owned because some job created it first). Root bypasses permission checks entirely, so `0777` on these internal, non-web-exposed directories is the actual fix, not a workaround to tighten later.
- **`romanzipp/laravel-queue-monitor` requires the `IsMonitored` trait per job class** — `monitor_queued_jobs => true` in its config only registers the listener, it does not auto-track every `ShouldQueue` job. `RunLogsFetch`/`RunImport`/`RunNormalize` use it (confirmed via a real `::dispatch()` through the actual queue, not a direct `handle()` call — the trait hooks `Queue::before`/`after` events that only fire for jobs actually processed off the queue). `PollCluster` deliberately does **not** use it — it fires every minute via the scheduler and would flood that table with a new row every 60s forever for no operational benefit.
- **Tab state (`x-data="{ tab: ... }"` in `pangolin/index.blade.php`) is synced to `?tab=` in the URL** two ways: server-side on load (`request('tab', 'monitor')`), and client-side via `x-init="$watch(...)"` calling `history.replaceState` whenever the Alpine `tab` value changes. Both are needed — the controller's own action methods (`logsFetch`, `resourcesImport`, `resourcesNormalize`) redirect to `route('pangolin.index', ['tab' => ...])` explicitly on success, but a **validation failure** redirects via Laravel's automatic `back()`, which follows the browser's `Referer` header — that header only has the right tab if the URL bar already had `?tab=` in it *before* the form was submitted, which is what the client-side sync guarantees.
- **`normalize_private_resources.py --resource-id` is numeric `siteResourceId` only** — but niceId is the only identifier users actually see (reports, the Pangolin dashboard). `App\Services\Pangolin\PangolinApiClient::resolveSiteResourceIds()` resolves non-numeric tokens against a live `GET /org/{org_slug}/site-resources` call (mirrors `get_site_resources()`/`api_headers()` in `normalize_private_resources.py` exactly — bearer token, `{data: {siteResources: [...], pagination: {...}}}` paginated shape) before `RunNormalize` builds `--resource-id` args. Confirmed live: resolved a real niceId to its numeric ID and got a correct scoped run back.
- **`accepted_if:apply,1` not `required_if:apply,1|accepted`** for the Normalize "confirm" checkbox. `accepted` (like `required`, `required_if`, `declined`) is one of Laravel's *implicit* rules — it runs even when the field is absent, independently of any other rule in the same pipe-separated list. Chaining it after `required_if` does not make it conditional; it always demanded the checkbox, including on plain dry runs. `accepted_if` is the actual conditional form.

## Authentik feature module

Integrates the `authentik-utils` Python toolset (vendored as a git submodule at `authentik-utils/`, upstream https://github.com/ktsouvalis/authentik — mirrors the Pangolin module's shape almost exactly, built 2026-08-03) behind a single menu entry and route (`/authentik`, route name `authentik.index`), one Blade page with **2** Alpine-driven tabs: Monitor and Logs. `import_users.py` (bulk CSV user import) exists in the submodule but was deliberately **not** wired up — this module is scoped to monitoring/observability only, by explicit request.

- **Monitor tab — native PHP, not a Python subprocess**, same rationale as Pangolin's: `monitor.py` is a Textual TUI with no headless/JSON mode. `app/Services/Authentik/ClusterMonitor.php` ports its HTTP checks (keepalived/VIP via nginx's `/monitor` JSON endpoint, Authentik `/-/health/live/`, Patroni, etcd, HAProxy stats CSV, nginx `/nginx_status`, plus the Authentik-API-token-gated worker/task-queue endpoints) directly via the `Http` facade — sequentially, not concurrently, matching how Pangolin's port was built (no `ThreadPoolExecutor` equivalent). `app/Jobs/Authentik/PollCluster.php` runs it and upserts `authentik_monitor_statuses` (one row per service+node, latest-only, same shape as `pangolin_monitor_statuses`); scheduled every minute in `routes/console.php` alongside Pangolin's poll. The tab polls `GET authentik/monitor/data` client-side every ~15s.
  - Unlike Pangolin's port, this one also carries Patroni's **`/history`** endpoint (failover timeline/reason/timestamp) since it's plain HTTP — shown as a line under the Patroni panel. Patroni's **replication-slots** check is intentionally unported, same call as Pangolin's Postgres-direct skip: `monitor.py` itself only populates slot data when `psycopg2` + Postgres credentials are both present (optional even in the original script), and porting it would mean adding a `pdo_pgsql` dependency for a cosmetic detail.
  - Cluster-wide singleton checks (`vip`, `workers`, `worker_queue`, `patroni_history` — none of which are really "per node") are stored as single rows keyed by the cluster VIP as `node_ip` rather than a specific node's IP, since the identity of e.g. the Patroni primary can shift between polls.
  - HAProxy status logic mirrors Pangolin's exactly: a backend pool is only flagged unhealthy when it has zero UP servers, not when any individual server is down (a Patroni-style pool at 1-of-3 UP is expected steady state). The rate/5xx-count columns `monitor.py`'s `HAProxyPanel` shows are *not* ported, matching how Pangolin's `ClusterMonitor::checkHaproxyNode()` simplified it — only up/down-per-pool is surfaced.
- **Logs tab — shells out to the submodule**, same pattern as Pangolin's Logs tab (chosen deliberately over a native SSH port, to keep both modules consistent). `app/Services/Authentik/ConfigYamlWriter.php` renders `config/authentik.php` into the `config.yml` shape `logs_viewer.py` expects, written per-run to `storage/app/private/authentik/runs/{id}/config.yml`; `app/Services/Authentik/ScriptRunner.php` wraps `Process` to run it there. `app/Jobs/Authentik/RunLogsFetch.php` owns one `authentik_log_runs` row per run (no `type` discriminator column — unlike `pangolin_runs`, there's only ever one run type here, so adding one would be premature) and uses `IsMonitored` for queue-monitor tracking, same as Pangolin's `RunLogsFetch`. There is no Newt-equivalent extra CSV output for this module.
- **SSH: a single key slot, not two.** `AUTHENTIK_SSH_USERNAME`/`AUTHENTIK_SSH_KEY_PATH` (+ `AUTHENTIK_SSH_KEY_HOST_PATH` for the bind mount) is the only SSH credential this module has — deliberately simpler than Pangolin's two-slot (cluster-nodes vs Newt-hosts) setup, since Authentik's 3 nodes are the only SSH target `logs_viewer.py` needs. Currently wired to reuse Pangolin's passphrase-less `pangolin_monitor_ed25519` key (`root@monitor`), authenticating as `ktsouvalis` — same key, different cluster (Authentik nodes `10.99.97.71-73` vs Pangolin's `10.99.97.51-53`), so its public half must independently be authorized on the Authentik nodes too. The real `authentik-utils/config.yml` on disk lists `ssh.key_file: ~/.ssh/id_ed25519_ktsouvalis_desktop` (a **passphrase-protected desktop key**) — that value was deliberately *not* carried into `.env`, since it's the exact category of key that already reliably failed headlessly for Pangolin (no stdin in the queue-worker container to answer a passphrase prompt). Don't reintroduce it here for the same reason.
- **Config/credentials**: same convention as Pangolin — `config/authentik.php` holds scalars via `env()`, with the real 3-node topology (`AUTHENTIK_NODES_JSON`, shape `[{"ip","name","base_priority"}]`) sourced from a JSON-encoded env var rather than hardcoded, since real cluster IPs are treated as sensitive and only ever live in the git-ignored outer `.env`. The `services:` list (which node group runs which docker/systemd unit, for `logs_viewer.py`) is a plain committed array in `config/authentik.php`, same as Pangolin's. **The app never reads `authentik-utils/config.yml` directly** — real values were transcribed once from that file into `developing/.env` / `production/.env` as `AUTHENTIK_*` vars; `ConfigYamlWriter` re-renders a fresh throwaway `config.yml` per Logs run from those config values, same flow as Pangolin's `ConfigYamlWriter`.
  - **`authentik-utils/config.yml`'s `credentials.haproxy_stats_pass` field literally contains the placeholder-looking string `HAPROXY_STATS_PASSWORD`** — it looks like an unfilled template value, but it is the actual, correct HAProxy stats password: verified live (`Http::withBasicAuth('admin', 'HAPROXY_STATS_PASSWORD')` → `200`; the Authentik API token tried as an alternative → `401`). Whoever configured HAProxy's stats auth apparently typed the placeholder text in literally. Don't "fix" this value without re-verifying against the live cluster first.
- **Python venv**: `AUTHENTIK_PYTHON_BIN` defaults to `/opt/authentik-venv/bin/python3` — a **separate** venv from Pangolin's `/opt/pangolin-venv`, built the same way in `developing/Dockerfile` (`COPY source/authentik-utils/requirements.txt` + `python3 -m venv` + `pip install`, right after the Pangolin venv step). Requires `git submodule update --init` for `authentik-utils/` before `docker compose build`, same caveat as Pangolin's venv step. `monitor.py`'s deps aren't needed since that script isn't invoked — only `logs_viewer.py`, which still imports `textual`/`rich` at module level even in `--save` mode. (Not yet mirrored into `production/Dockerfile` — do that before enabling this module in production.)
- **Access control**: `app/Http/Middleware/AuthentikEnabled.php` mirrors Pangolin's **current** behavior (not its original one) — menu-enabled check only, no `admin`-only gate, matching the `pangolin middleware: allow any authenticated user, not just admins` change. The Menu row's `route_is` must be the literal string `authentik` (not `authentik.index`), same reasoning and same cosmetic nav-highlight gap as Pangolin's.
- **`storage/app/private/authentik/` needs the same `0777`-on-directories treatment as `storage/app/private/pangolin/`** — written by both the root-running queue-worker and the www-data web process; see the Pangolin section above for the full rationale, it applies unchanged here.
